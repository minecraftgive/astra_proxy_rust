# 自适应缓冲与常驻内存优化

目标：低负载减少分配，高吞吐时恢复原容量，高并发仍受现有配额约束。配置和管理协议不变。下面的缓冲容量是用户态存储容量，不等于进程 RSS；索引、协议库、分配器保留页及重分配瞬时峰值另计。

## 行为

| 资源 | 起始容量 | 最大容量 | 回收条件 |
|---|---:|---:|---|
| 客户端 TCP relay，每方向 | 4 KiB | 32 KiB | 无待写数据，空闲 30 秒 |
| 服务端 TCP relay，每方向 | 4 KiB | 16 KiB | 无待写数据，空闲 30 秒 |
| TUN 暂存环，每方向 | 4 KiB | 64 KiB | 环为空，空闲至少 30 秒，在栈维护时回收 |
| DNS 缓存、映射 HashMap | 按需分配 | 现有条目/报文字节上限 | 清除过期条目，低于容量四分之一持续 30 秒后缩小存储 |

Relay 在 100 毫秒内连续四次完成整缓冲读写后翻倍；只有全部待写数据完成后才能换存储。短读、慢速传输不会触发这类扩容。读端停顿时才注册回收定时器，热路径不逐包重置定时器。EOF 完成后立即释放该方向的存储，独立半关闭、写入背压和取消语义保留。

TUN 的暂存环满且仍有待处理数据时翻倍，换环时按原顺序搬移未消费数据。TCP 协议窗口仍为每方向 256 KiB，256 个 socket 上限不变；窗口和暂存环容量总上限仍为 160 MiB。UDP 接收缓冲保持完整报文容量。服务端 UDP 既有流不再每包扫描整张流表，清理在任务结束、周期维护及容量不足时执行。

DNS 保存规范化查询键和紧凑响应报文，命中后在锁外解析、恢复事务 ID 并扣减 TTL。应答和查询历史共用已经解析的 Message，避免为记录历史重复解析或深拷贝。缓存字节数增量维护；到期和写入顺序索引各至多一项对应一个存活条目，重复刷新不积累过期索引。

Fake-IP 用域名/地址族索引查找已有地址，正反向索引共享域名文本；续期替换到期索引，过期同时清理两端。活跃映射不会因缩容被驱逐，热重载和宿主所有权仍保持一致。新增索引会增加满载映射表的内存，这是消除线性查找的明确取舍。

每个 DNS 缓存和本地映射所有者至多一个五秒维护任务。任务仅弱引用存储，所有者释放时取消任务；不为每个查询、映射或连接建立清理任务。

规则的原文及规则序号与匹配器分离：组合正则构建成功后丢弃单条编译结果，组合构建失败时仍用逐条匹配。规则优先级和解释输出不变。GUI 日志行共享不可变文本，暂停快照不再复制全文；视图按会话对象、实际显示内容和筛选条件缓存筛选结果与最大宽度，重绘只构造可见行。暂停后的新日志、连接状态变化不重建呈现缓存；缩小历史上限和切换会话会正确更新。视图销毁时释放呈现缓存。

## 监控

- `buffer.copy.bytes/grows/shrinks`：转发缓冲当前容量、增长和空闲收缩次数；连接释放只影响容量。
- `buffer.tun.bytes/grows/shrinks`：TUN 暂存环当前容量、增长和收缩次数；分配/释放回调更新，无额外采样任务。
- `dns.cache.entries/bytes`：当前缓存条目、查询键与响应报文字节总量，不含索引元数据。
- `dns.mapping.fake.entries`、`dns.mapping.real.entries`：当前映射条目。
- `dns.maintenance.active`：存活维护任务数。

计数覆盖本进程的所有相应对象，不使用域名、连接 ID 等高基数标签。RSS 仍由已有进程监视器采集，不能用上述容量指标替代。

## 验证方法

- 单元测试覆盖 20 轮扩容/回收、环形回绕后的字节顺序、部分写入和背压、中断重试、缓冲写端刷新、异步半关闭、取消、缓存替换/过期/预算、续期索引不增长、负载突发重置回收宽限期以及维护任务释放。日志测试覆盖暂停共享与缓存复用、筛选、历史裁剪和相同行数的会话替换。
- 20 轮资源循环使用虚拟时钟或显式推进维护时间，断言实际缓冲长度、容器容量和索引数量回落；这不是 20 轮真实进程 RSS 回落曲线。
- 普通/hosted、direct/group、1千/1万规则、冷/热缓存、并发 1/32 使用 `scripts/optimization_benchmark.py` 交错测试，固定各版本的二进制并记录 SHA-256。吞吐下降超过 3% 或 p95/p99 增长超过 5% 自动扩展复测。
- `scripts/memory-benchmark` 是独立的原生合成负载程序，使用两边相同的计数 System allocator；覆盖 8192 项 DNS 缓存、8192 项 Fake-IP、2000 条正则、8000 行暂停日志的重复呈现。基线用 `--features legacy` 复现旧日志呈现路径，新版本使用呈现缓存。
- `scripts/memory_benchmark.py` 对两份原生负载程序执行至少五轮交错测量，记录热循环吞吐/分位数、当前/峰值请求分配量、进程 CPU、采样峰值 RSS 和保留负载时的 RSS。进程 CPU 包含预热/构建；热循环时间不包含预热/构建。日志结果是模型与行准备成本，不是 GPU 帧率。
- `scripts/native_network_benchmark.py` 提供共用原生负载端的补充诊断：两边使用同一客户端/回显程序，记录额外的 EOF 等待分位数，避免把负载端实现差异当作代理变化。
- Windows/Linux 没有本轮实机数据；本机环回吞吐不代表加密长链路、真实 TUN 或生产最大容量。

macOS 测试临时目录须短、属于当前主组且使用规范路径（例如 `/private/tmp/am.XXXX`）；否则部分既有管理器/安装测试会受到 Unix socket 路径长度、组权限或 `/tmp` 符号链接检查影响。平台 socket 所有权测试单独串行运行，避免其他测试启动的子进程短暂继承锁。

最终版本的七个相关 crate 单元测试共 **680 项通过、7 项跳过**；更早的全工作区功能回归为 **1442 项通过、32 项跳过**，后续针对修改处重测，两个数字不累计。DNS 集成测试、独立 netstack 测试和基准脚本测试也通过。本地发布构建的 **19 组协议/传输组合**全部互通，覆盖 TCP 1 字节至 1 MiB、UDP 0 至 8192 字节及重载/停止；这属于正确性验证，不是加密长流性能对照。

严格 `clippy -D warnings` 仍受既有警告阻挡：IPC telemetry 和 DNS upstream 的复杂类型、system_dns 枚举名、runtime controls 的多余引用，以及既有测试中的字段初始化/转换。普通 workspace Clippy 完成，本轮修改未增加警告。

## 本机专项对照结果

基线为 `074363b`，macOS arm64，Apple M3 Pro、12 个逻辑 CPU、36 GiB 内存、Rust 1.98.0。同机 release，五轮交错运行，每个版本各 20 次专项进程。下表为各轮中位数；MiB 为 1,048,576 字节。分配量包含整个合成负载进程仍持有的请求分配；RSS 在负载仍存活时采样，包含分配器保留页。

| 场景 | 持有分配量 MiB，前 → 后 | RSS MiB，前 → 后 | 吞吐变化 | p95 / p99 变化 |
|---|---:|---:|---:|---:|
| 8192 项 DNS 缓存命中 | 46.45 → 9.50 | 64.03 → 18.08 | +9.83% | -10.20% / -7.82% |
| 8192 项 Fake-IP 复用 | 5.59 → 6.87 | 13.70 → 15.06 | +661.36% | -88.89% / -88.74% |
| 2000 条正则匹配 | 53.25 → 8.40 | 83.58 → 80.75 | +1.52% | -1.29% / -1.99% |
| 8000 行暂停日志的行准备 | 4.20 → 2.61 | 13.50 → 9.53 | 见说明 | -99.99% / -99.99% |

四项均通过吞吐 −3%、p95/p99 +5% 门槛。首轮紧凑 DNS 缓存测试曾出现吞吐 −4.19%，因此进一步去除了应答及查询历史的重复解析，再进行独立五轮复测；表中为修正后的结果。

Fake-IP 新增索引带来约 1.36 MiB RSS 增量及 22.82% 持有分配增量，换取满表复用吞吐约 7.61 倍；这项改动并非满载内存优化。正则持有分配量下降 84.23%，RSS 仅下降 3.38%，构建峰值分配仍约 65.8 MiB，不能把已释放分配直接当作 RSS 降幅。日志重复行准备从每次扫描/复制变为缓存命中，测得吞吐约 557.71 倍；该数字仅描述合成模型操作，不代表整页渲染或 GPU 帧率。

原始专项结果保存在 `target/adaptive-memory/native-v3.json`，先前失败的 DNS 对照保存在 `target/adaptive-memory/native-comparison.json`。复现时将相同的 `scripts/memory-benchmark` 目录放入基线和当前源码树，分别构建：基线添加 `--features legacy`，当前不添加。

```sh
cargo build --locked --release --manifest-path scripts/memory-benchmark/Cargo.toml
python3 scripts/memory_benchmark.py --before /path/to/before/astra-memory-benchmark --after /path/to/after/astra-memory-benchmark --rounds 5 --output /path/to/native-comparison.json
python3 scripts/optimization_benchmark.py --before /path/to/before --after /path/to/after --rounds 5 --max-rounds 10 --output-dir /path/to/network-comparison
```

测量时停止编译和其他测试；两边使用相同依赖锁文件、负载程序和采样程序。网络脚本记录各进程和总 RSS/CPU；原生专项每次只有一个负载进程。Windows/Linux、真实 TUN 与加密服务端长流尚无本轮性能实测，不能从上述结果推断。

## 端到端验收状态

**实现和功能验证已完成，端到端性能验收仍未通过；不作为已达到合入标准的改动交付。** 原生 DNS、规则、日志专项通过门槛，但当前本机网络测试不能可靠判定吞吐 −3%、p95/p99 +5% 的小幅差异。

首组普通/hosted 对照已从五轮扩展到十轮，仍有短连接指标超标。随后使用共用原生负载端补充诊断，并尝试跳过 macOS 未实现的进程查询所创建的后台任务；该额外改动没有得到稳定的端到端收益支持，已完全撤回，最终源码保留原有进程查询路径。所有失败和中止的试验均保留。

为核对测量精度，再用**完全相同的基线二进制**执行五轮交错对照，两个标签的 SHA-256 相同。其中 1000 规则、禁用缓存、并发 32 的连接吞吐中位数仍相差 −47.05%，建连 p99 相差 +64.75%。这说明现有条件下的测试波动明显大于验收门槛；既不能把这类差异直接归因于代码，也不能据此宣布优化无回退。需要在更稳定的端到端测试环境完成最终放行，当前未提交、未合入。

对照记录：`target/adaptive-memory/network/comparison.json`（首组十轮）、`native-network/comparison.json`（原生负载补充诊断，中止）、`network-final/comparison.json`（已撤回的额外优化试验）、`same-binary-control/comparison.json`（同版本五轮控制）。后面三个相对路径同样位于 `target/adaptive-memory/`。原生专项的确定性分配量收益、实际 RSS 与端到端性能门槛分别报告。

可随源码保存的测量数据、样本、二进制哈希、每进程资源记录与验收状态见 [adaptive-memory-results.json](adaptive-memory-results.json)。
