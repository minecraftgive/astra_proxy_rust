# 架构评价与实际改进方案

审查日期：2026-10-18。约束：原生 Rust 协议实现，不引入外部代理核心；建议仅针对性能、使用体验与故障修复。

## 结论

保留 Proxy Core / Rule Core 双进程及元数据 IPC。当前载荷不经过规则进程，规则索引保留全局第一匹配语义，缓存与持久连接避免重复工作，资源上限覆盖 TCP 会话和 UDP 流。这些设计与当前目标相容。

双进程增加冷路由的一次本地往返和进程管理成本；它提供生命周期隔离，但没有整机性能数据证明比单进程快。当前不需要为架构整齐拆更多服务，也没有证据支持替换为共享内存、io_uring 或自行实现 TLS。

## 按收益排列的工作

| 优先级 | 证据与实际影响 | 改进方案 | 验收方式 |
|---|---|---|---|
| P1 修复 | 普通 VMess UDP 已补齐；REALITY UDP 经修正探针时限后复测通过。部分路径的大包/空包边界仍失败。用户选择可用 TCP 节点后，UDP 应用可能不可用 | 补齐逐包原生实现；保持报文边界、远端域名解析及取消后的状态一致性；不能支持的模式提前说明或拒绝 | 与参考服务端互通：IPv4/IPv6/域名、空包、典型 MTU、8192 字节；混合双向负载与关闭清理 |
| P1 修复 | `inbound.rs` 的双向复制无法保证底层协议 EOF 语义。VLESS/Xray 的严格半关闭测试仍失败，packet-up 当前关闭整个隧道 | 分别定位客户端传输、协议包装和服务端；保留独立半关闭测试。对无独立上传 EOF 的模式明确限制，避免声称通用半关闭 | 上传结束后目标延迟发送响应和 trailer，验证完整接收及无悬挂；不支持的模式给出明确结果 |
| P1 QOL | 旧 README 同时声称 UDP、TUIC、XHTTP packet-up 未实现，与当前代码冲突 | 本次已重写支持范围、原生构建依赖、启动步骤与路由示例；将未通过的组合留在验收清单 | 配置检查通过；文档所列基础配置与互通矩阵一致 |
| P2 QOL/策略修复 | `main.rs::route_network` 命中缓存直接返回；规则进程重启不通知缓存，默认可继续使用旧决策 5 秒 | 若需要即时策略切换，增加规则版本通知及代理缓存失效；必须覆盖已有持久 IPC 通道。先明确既有 TCP/UDP 流是否保留，不把“清缓存”等同于撤销已有连接 | 修改规则并重启后，缓存命中的新连接立即使用新策略；已有流行为按文档执行；规则断线不回退直连 |
| P2 QOL | 会话失败主要记录在 debug 日志；用户通常只看到连接失败，难区分规则、DNS、认证、TLS、目标拒绝 | 为失败增加阶段与出站标签；正常断连避免告警，重复错误汇总限频，不记录凭据或载荷 | 注入规则不可用、错误密码、错误 SNI、目标拒绝和超时，日志能够直接定位阶段 |
| P2 性能 | 缓存未命中时每请求占一个 IPC 通道；尚无排队时间和新建连接延迟基线。现有名为 mixed_rules 的微基准实际只有一条后缀规则 | 先补 1千/1万/10万混合规则及冷/热目标负载，记录 p50/p95/p99、CPU、RSS、吞吐与 IPC 等待；据结果调整连接池或合并相同目标的并发查询 | 相同机器、release 构建、相同负载多次对比；仅保留降低实际延迟/CPU且不恶化内存和尾延迟的改动 |
| P2 性能 | packet-up 当前固定 64 KiB 分块、4 个并发 POST；每连接有界，但适配不同 RTT 的效果未测 | 用本地和延迟链路测交互小包与长流，再考虑受限可配置窗口；不能仅为吞吐无限扩大队列 | 吞吐、首字节延迟、取消释放时间和多连接峰值 RSS 一起比较 |

P1 为完整首版验收前优先处理；P2 依据实际部署需求或测量结果决定。性能项是待验证假设，当前没有宣称提升百分比。

## 已有修复应保留的保障

- IPC 的一个总期限覆盖等待通道、连接和重试；超时/取消不把半读通道归还池。
- 监听器先接收连接再申请额度，避免空闲监听器占住名额。
- 首包读取不会阻塞必须先发送请求的客户端。
- UDP 区分网络类型缓存、限制目标/队列、绑定客户端来源，随控制连接关闭。
- TUIC 共享 QUIC 连接，并对分片、接收任务及总排队字节设限。
- XHTTP packet-up 对 POST 顺序、确认、错误及任务取消有独立测试。

## 本轮验证

- `cargo test --workspace`：18 项通过，1 项手动规则微基准忽略。
- `cargo clippy --workspace --all-targets -- -D warnings`：通过；vendored 依赖仍有两条已有的 BoringSSL API 弃用警告。
- 完整 TCP 参考服务端矩阵：24 组均通过 64 KiB 回显与收到回显后的关闭。
- XHTTP packet-up UDP：IPv4/IPv6/域名，1..4096 字节通过。

上述是 debug 构建的功能验证，不是 release 性能基线，也不是所有组合通过生产验收的证明。

后续同日验证：原生 VMess UDP 对 Xray 通过 1..4096 字节，对 sing-box 通过空包至 8192 字节；14 项 VMess 编解码测试通过。REALITY UDP 修正探针期限后两次复测通过。VMess 的 8 MiB 上传 EOF 后响应测试在 sing-box 通过、在 Xray 丢失 trailer，仍需定位服务端差异。

首版结项复核：协议补齐、文档与错误/取消测试已完成；Xray 半关闭和 UDP 边界通过独立客户端及第二服务端对照记录为兼容性限制。详细现状以 COMPATIBILITY.md 与 V1_ACCEPTANCE.md 为准。此文中的缓存版本通知、诊断日志及进一步性能调优为后续建议，并未承诺随 0.1.0 实现。
