## 内存与测试端开销

这里只采样 Windows 进程私有内存与工作集，不是逐次分配统计，也不是内存泄漏验收。TUN 会保留尚未到默认空闲期限的 UDP 流，轮次间的内存增长不能直接认定为泄漏。

| 模式 | 代理私有内存起止范围 MiB | 代理采样峰值私有内存 MiB |
|---|---:|---:|
| normal | 3.53–4.35 | 4.82 |
| system-proxy | 4.48–6.64 | 6.64 |
| tun | 9.02–13.98 | 17.98 |

原始报告分别记录代理、原生上游、负载端 CPU；WinINet HTTP 组记录 Python 调用端 CPU。不能把它们加总后都归到代理。初次 TUN 长循环在第 3 轮出现一次 UDP 超时；随后发现测试上游给 UDP 的闲置 TCP 控制连接设了 30 秒期限，移除后重新完成全部三轮。初次失败未混入最终中位数，也未单独据此认定为产品缺陷；失败摘要保存在原始记录中。

## 对零拷贝的判断

- **小消息首先排查每消息开销。** 普通代理 64 B 消息只有约 0.8 MiB/s，但 CPU 约 2.8 核；单凭这点不能认定是复制字节量耗尽带宽。任务唤醒、socket 调用、队列、分配等仍需采样区分。
- **TUN 有优先级更高的延迟异常。** IPv6 64 KiB 消息重复得到约 5.5 MiB/s、p50 约 45 ms，而代理 CPU 仅约 0.2 核；同一路径 1 MiB 消息反而约 56 MiB/s。这更提示等待/批量边界问题，应先定位 TCP ACK、窗口和协议栈调度，尚不能确定具体原因。
- **大消息存在优化空间，但没有证明全面零拷贝是首选。** 普通代理 1 MiB 消息约 239 MiB/s，低于同机原生上游基线约 951 MiB/s；两者经过的 socket 和转发层不同，差额不能全部算作 memcpy。
- 下一步应先对 TUN 延迟异常做定点诊断，再对复用缓冲、减少包级分配和读写批量做单变量对比。当前没有分配栈或 CPU 调用栈数据，不报告“零拷贝可提升多少”的推算。

系统代理测后逐项恢复到原设置；TUN 只接管两个专用测试主机路由，退出后设备和路由均清理。未修改客户端/服务端打包布局，本次没有修改产品的转发或拷贝实现。

## 复现

先在本机准备优化构建，并把 Wintun 放到该程序旁。编译原生负载端：

```powershell
rustc -O scripts/windows_load.rs -o .test-tools/windows-load/windows-load.exe
python scripts/windows_load.py --mode normal --profile release --bin-dir .test-tools/windows-load/bin --output-dir .test-tools/windows-load/normal --seconds 3 --rounds 3 --concurrency 4
python scripts/windows_load.py --mode system-proxy --profile release --bin-dir .test-tools/windows-load/bin --output-dir .test-tools/windows-load/system-proxy --seconds 3 --rounds 3 --concurrency 4
# 管理员终端；27 替换为实际物理出口索引：
python scripts/windows_load.py --mode tun --profile release --bin-dir .test-tools/windows-load/bin --output-dir .test-tools/windows-load/tun-retest --interface 27 --seconds 3 --rounds 3 --concurrency 4
```

三个模式顺序执行，不要并行测速。原始三轮数据及失败摘要见 [windows-load-results.json](windows-load-results.json)。
